# Frontend–backend integration audit

Audit of the supplied frontend and sibling `backend-main` source. This is a static contract audit; routes present in source are not evidence of a running service or a completed workflow. The backend uses **Fiber v3**, not Gin. Its README and older module-status/workflow documents describe different milestones; the route handlers and services are the reference for the table. No `AGENTS.md` or `PHASES.md` was found in the supplied workspace. After the audit, the frontend was adjusted to preserve unedited patient fields, use separate patient permissions and match staff role values; production remains gated and development opt-in is unverified.

The table records the initial audit, before the subsequent frontend work described below. All paths are relative to the frontend and backend roots respectively. Staff endpoints use the prefix `/api/v1/staff`; authentication uses `/api/v1/auth`. Except login, MFA verification, refresh, and password reset, endpoints require a bearer access token. Handler permissions below are supplemented by service-level permission, facility, patient-care and database row-security checks; an empty handler permission is **not** public access. `items` is a JSON list wrapper, and `paged` adds `next_cursor`. Exact optional fields, validation and responses are in the named backend source and OpenAPI; raw JSON objects are based on database columns, not a stable frontend DTO yet.

## Schema and data flow

Migrations `0002`–`0009` define organization/membership/session, audit, patient, clinical encounter/appointment/queue, diagnostics/pharmacy/documents, billing and telehealth relations; subsequent migrations add API support and workflow guards. An encounter links patient, facility and optionally appointment; clinical, diagnostic, prescription and invoice records link through encounter/patient. Inspect the migrations and `db/docs/data_dictionary.md` for constraints and SQL RLS. Never connect the browser to PostgreSQL.

## Subsequent frontend work and backend issue

The development-only adapter now has read-only appointment and active queue views using `GET /staff/appointments` and `GET /staff/queue`; both remain unverified against a running backend. Booking, check-in and queue changes are unavailable. Appointment pagination is deliberately limited to the first page: `telehealth.ListAppointments` orders by `scheduled_start DESC, id` but filters the cursor using only `id > cursor`. This can skip or repeat rows across pages. The backend engineer should review the ordering and cursor contract before pagination is enabled; no backend files were modified.

## Development boundary

The example backend binds `127.0.0.1:8080`, API prefix `/api/v1`, and allows only `http://localhost:3000` by default. The frontend currently uses `127.0.0.1:5173`, so the origins differ. Backend web login, MFA, refresh and logout enforce exact Origin; web refresh uses `SameSite=Strict`, so the browser host names must also be same-site. Deployment must independently confirm HTTPS, cookie, proxy and Origin configuration.

No backend `.env` or isolated local PostgreSQL setup was present in the supplied tree. Backend tests that create/drop disposable databases require an explicitly authorized test database; the supplied test harness must never target production. Do not infer an available development database or credentials from a local installation.
